## Правила работы AI с `.param` файлами

Эти правила выросли из **реального инцидента** (см. Lessons ниже): в первом проходе анализа Cube Orange + ELRS AI выдал 4 неверных рекомендации, которые при проверке по официальной документации оказались ошибочными. Чтобы это не повторялось:

### Инвариант 1: НЕ доверять памяти

Прежде чем рекомендовать значение параметра — **обязательно проверить по официальной документации**. Источники для проверки:
- **ArduPilot:** https://ardupilot.org/copter/docs/parameters.html
- **ExpressLRS:** https://www.expresslrs.org/quick-start/ardupilot-setup/
- **CubePilot:** https://docs.cubepilot.org/user-guides
- **Betaflight Wiki:** https://github.com/betaflight/betaflight/wiki

При сомнении — подтянуть свежую страницу по конкретному параметру (в claude.ai — `web_fetch`, в Claude Code — `WebFetch`).

### Инвариант 2: Формат рекомендаций — всегда таблицей

Каждая рекомендация по `.param` — таблица с обязательными колонками:

| Параметр | Было | Стало | Почему |
|---|---|---|---|
| `RSSI_TYPE` | 2 | **3** | 3 = ReceiverProtocol — берёт RSSI из CRSF, не из RC-канала |

Никаких «поменяй `RSSI_TYPE` на 3» без указания «было» и «почему». Без «почему» правка может оказаться вредной.

### Инвариант 3: Учитывать связи между параметрами

Многие параметры взаимосвязаны (битовые маски, зависимости версий прошивки, аппаратные ограничения). Перед советом проверять:

- **Не отменяется ли изменение другим параметром.** Классический пример: `RC_OPTIONS = 8708` имеет бит 13 (значение 8192), который переопределяет `SERIAL4_BAUD` на 420k baud — менять `SERIAL4_BAUD` отдельно бессмысленно.
- **Совместимость с версией прошивки** (Copter 4.5 vs 4.6 могут отличаться).
- **Аппаратные зависимости.** Например, DShot на Cube Orange работает ТОЛЬКО через AUX выходы, не MAIN.

### Инвариант 4: Цитировать источники

В каждой рекомендации — **ссылка на конкретную страницу документации**. Если ссылку найти не удалось — **явно говорить:** «не подтверждено документацией, проверь на железе осторожно». Не выдавать предположение за факт.

### Инвариант 5: Безопасные правки

Перед изменением `current.param` сборки:

1. Скопировать текущий в `history/YYYY-MM-DD.param`
2. Сделать правки в новом файле
3. Применить через Mission Planner → Write Params → перезагрузка FC
4. Проверить эффект на стенде (props off!) перед полётом
5. Задокументировать в `incidents/`

### ⚠️ Категорически опасные параметры — НЕ менять без явного запроса пользователя

При любой попытке тронуть эти параметры — сначала **предупредить ⚠️ и обосновать**:

- `FRAME_CLASS`, `FRAME_TYPE` — неправильно → дрон перевернётся / не полетит
- `ARMING_CHECK = 0` — обход всех проверок арминга
- `FS_THR_ENABLE = 0` — отключение RC failsafe
- `MOT_SPIN_ARM`, `MOT_SPIN_MIN` без тестирования — моторы могут останавливаться в воздухе
- `BRD_SAFETYENABLE = 0` — отключение safety switch
- Любые `EK3_*` без понимания EKF
- `SCHED_LOOP_RATE` выше 400 — риск перегрузки CPU и нестабильности

Если пользователь сам просит — окей, но с предупреждением ⚠️ и явным разбором рисков.

## Правила работы AI с инцидентами

При совместном разборе проблемы — сразу создавать `builds/<сборка>/incidents/YYYY-MM-DD-короткий-симптом.md` по шаблону:

```markdown
# YYYY-MM-DD · Краткий симптом одной строкой

## Симптом
1–3 предложения: что увидел пользователь.

## Контекст
- Сборка: <имя>
- Прошивка: ArduCopter X.Y.Z
- Что менялось в последний раз: ...

## Диагностика
- Что проверили в логах / на стенде / в Mission Planner
- Что нашли

## Решение

| Параметр | Было | Стало | Почему |
|---|---|---|---|
| ... | ... | ... | ... |

## Источники

- ссылки на docs.ardupilot.org / expresslrs.org / другие official docs

## Проверка на железе

- [ ] Применено в Mission Planner
- [ ] Перезагружен FC
- [ ] Проверено визуально (что именно — например «OSD показывает реальный LQ 0–100%»)
- [ ] Прошло проверку в полёте
```

После закрытия инцидента (всё проверено на железе) — итог переносится в накапливающий `ANALYSIS.md` сборки. Сам инцидент остаётся в `incidents/` для истории.

## Lessons & Incidents

> Глобальные уроки уровня всего workspace. Уроки уровня одной сборки — в `builds/<имя>/incidents/`.
> Новые записи добавляй **сверху**. После каждого крупного разбора задай себе вопрос:

### 2026-03-05 · AI выдал пачку неверных рекомендаций по ELRS+ArduPilot

В первом проходе анализа Cube Orange + ELRS + Walksnail AI рекомендовал 4 правки, которые при перепроверке по официальной документации оказались **неправильными или ненужными:**

1. `SERIAL4_BAUD = 115 → 420` — неверно, т.к. `RC_OPTIONS` бит 13 уже переопределяет на 420k baud.
2. `RC_SPEED = 490 → 0` — неверно, `RC_SPEED` это частота ESC PWM, к ELRS не относится вообще.
3. `RC_OPTIONS = 8708 → 768` — неверно, в новом значении пропал бит 13 (420k baud).
4. `SCHED_LOOP_RATE = 400 → 800` — рискованно без тестирования, рекомендация официально не поддержана.

Подробности — `builds/cube-orange-elrs-walksnail/ANALYSIS.md` Часть 2.

**Правило:** **никогда не давать рекомендацию по `.param` без явной ссылки на актуальную документацию.** Если ссылку найти не удалось — явно говорить «не могу подтвердить, не меняй».

**Проверка:** в каждом ответе про параметры должна быть хотя бы одна ссылка на ardupilot.org / expresslrs.org / docs.cubepilot.org. Если ссылок нет — это сигнал, что я отвечаю по памяти, и это плохо.

## Commands

В этом workspace нет автоматизированных проверок (это knowledge-base, не Python-приложение). Минимальная гигиена через git:

| Команда | Что делает |
|---|---|
| `git status` | проверить, что не оставил недокоммиченные файлы |
| `git log --oneline -20` | посмотреть историю последних 20 правок |
| `git mv <old> <new>` | переименование с сохранением истории (важно для `builds/`) |
| `git diff --stat` | какие файлы изменились в текущем рабочем дереве |

В подпапках (`tools/`, `companion/`) могут появляться Python-подпроекты со своими `pyproject.toml` и `verify.ps1` — по шаблону `u1u2-bridge`. Каждый такой подпроект сам определяет свой verify-контракт.

## Что НЕ делать в этом workspace

- **Не класть прошивку Mission Planner / ArduPilot installer'ы** — они большие, версионируются у вендора.
- **Не коммитить полётные логи (`.bin`, `.tlog`)** — могут быть огромные, должны быть в `.gitignore`.
- **Не коммитить приватные ключи** (WireGuard, SSH, и т.п.) — `.gitignore` это покрывает.
- **Не дублировать содержимое скилов** в `notes/` — скилы живут на уровне Claude-аккаунта, в `notes/` только то, чего там нет.
